Spring IoC

IoC和DI

IoC（Inverse of Control，控制反转）：将对象的创建、管理、销毁交给Spring容器管理，而不是程序自己new，实现解耦

DI（Dependence Injection，依赖注入）：IoC的一种是实现方式，在创建对象时，用容器将其依赖的对象注入进来

Bean生命周期

能说主要阶段：实例化 → 依赖注入 → 初始化（@PostConstruct）→ 使用 → 销毁

Bean的作用域

Spring 中 Bean 的作用域通常有下面几种：

  • singleton（单例） : IoC 容器中只有唯一的 bean 实例。Spring 中的 bean 默认都是单例的，是对单例设计模式的应用。
  • prototype （原型）: 每次获取都会创建一个新的 bean 实例。也就是说，连续 getBean() 两次，得到的是不同的 Bean 实例。
  • request （仅 Web 应用可用）: 每一次 HTTP 请求都会产生一个新的 bean（请求 bean），该 bean 仅在当前 HTTP request 内有效。
  • session （仅 Web 应用可用） : 每一次来自新 session 的 HTTP 请求都会产生一个新的 bean（会话 bean），该 bean 仅在当前 HTTP session 内有效。
  • application/global-session （仅 Web 应用可用）：每个 Web 应用在启动时创建一个 Bean（应用 Bean），该 bean 仅在当前应用启动时间内有效。
  • websocket （仅 Web 应用可用）：每一次 WebSocket 会话产生一个新的 bean。

Bean的声明

  • @Component：通用的注解，可标注任意类为 Spring 组件。如果一个 Bean 不知道属于哪个层，可以使用@Component 注解标注。
  • @Repository : 对应持久层即 Dao 层，主要用于数据库相关操作。
  • @Service : 对应服务层，主要涉及一些复杂的逻辑，需要用到 Dao 层。
  • @Controller : 对应 Spring MVC 控制层，主要用于接受用户请求并调用 Service 层返回数据给前端页面。

Bean的注入

  • 构造器注入（推荐）
  • Setter注入（可选依赖项）
  • 字段注入（@Autowired或@Resource，不推荐但常见）
  • 方法注入（少用）

@Autowired vs @Resource

比维度 @Autowired @Resource
来源 Spring 框架提供（org.springframework.beans.factory.annotation.Autowired） Java 标准（JSR-250，javax.annotation.Resource）
注入顺序 先按类型（byType），若有多个再按名称（需要 @Qualifier） 先按名称（byName），若名称找不到再按类型
属性支持 只有一个 required 属性 有 name 和 type 两个属性，可分别指定
支持位置 构造器、字段、Setter 方法、普通方法 字段、Setter 方法（不支持构造器）
是否强制 required 默认 true，找不到 Bean 会报错 默认要求必须存在，找不到也报错（可通过 @Resource(name="...") 指定）
配合注解 可配合 @Qualifier 指定名称 通过自身的 name 属性指定名称

循环依赖

  • 循环依赖：A 依赖 B，B 依赖 A。
  • 三级缓存：
    • 一级缓存：singletonObjects（完整 Bean）
    • 二级缓存：earlySingletonObjects（早期暴露的 Bean，未完成属性填充）
    • 三级缓存：singletonFactories（ObjectFactory，可生成早期 Bean 或代理对象）
  • 解决原理：实例化 A 后，将 A 的 ObjectFactory 放入三级缓存，然后填充 A 属性时发现需要 B，去创建 B；B 填充属性时发现需要 A，从三级缓存中获取 A 的早期引用（可能生成代理），B 完成创建；A 完成属性填充，最终成为完整 Bean。
  • 注意：只能解决单例的 setter 注入循环依赖，构造器注入无法解决（因为实例化前就需要依赖）。prototype 作用域也无法解决。

Spring AOP

Spring AOP 是 Spring 框架的核心功能之一，它通过动态代理实现了面向切面编程，主要用于将横切关注点（如日志、事务、权限）与业务逻辑解耦。Spring AOP 是一种通过动态代理实现横切逻辑织入的技术，核心是切面、切点、通知三大要素。它让开发者在不侵入业务代码的情况下，优雅地处理日志、事务、权限等通用功能，是现代 Java 后端开发中不可或缺的基础设施。

基本概念

AOP（Aspect-Oriented Programming，面向切面编程）允许在不修改原有代码的情况下，为程序动态添加额外功能。它解决了传统面向对象编程难以处理的横切关注点问题。

术语 说明
切面（Aspect） 横切关注点的模块化，一个类，内部包含通知和切点
连接点（Join Point） 程序执行过程中的一个点，如方法调用。Spring 只支持方法级别的连接点
切点（Pointcut） 匹配连接点的表达式，用于指定哪些方法需要被增强
通知（Advice） 在切点匹配的方法上执行的具体增强逻辑
目标对象（Target） 被代理的原始对象
代理（Proxy） 将通知应用到目标对象后生成的新对象
织入（Weaving） 将切面应用到目标对象并创建代理对象的过程

通知类型

  • Before（前置通知）：目标对象的方法调用之前触发
  • After （后置通知）：目标对象的方法调用之后触发
  • AfterReturning（返回通知）：目标对象的方法调用完成，在返回结果值之后触发
  • AfterThrowing（异常通知）：目标对象的方法运行中抛出 / 触发异常后触发。AfterReturning 和 AfterThrowing 两者互斥。如果方法调用成功无异常，则会有返回值；如果方法抛出了异常，则不会有返回值。
  • Around （环绕通知）：编程式控制目标对象的方法调用。环绕通知是所有通知类型中可操作范围最大的一种，因为它可以直接拿到目标对象，以及要执行的方法，所以环绕通知可以任意的在目标对象的方法调用前后搞事，甚至不调用目标对象的方法

实现原理

Spring AOP 就是基于动态代理的，如果要代理的对象，实现了某个接口，那么 Spring AOP 会使用 JDK Proxy，去创建代理对象，而对于没有实现接口的对象，就无法使用 JDK Proxy 去进行代理了，这时候 Spring AOP 会使用 Cglib 生成一个被代理对象的子类来作为代理。

应用和失效场景

常见应用场景

  • 声明式事务：@Transactional 基于 AOP 实现，方法执行前后管理事务。
  • 日志记录：统一打印方法入参、出参、耗时。
  • 权限校验：在方法执行前验证用户权限。
  • 缓存：结合 @Cacheable，在方法执行前查询缓存，执行后更新缓存。
  • 性能监控：统计方法执行时间，发现慢查询。

常见失效场景

  1. 同类内部方法调用：在同一个类中，方法 A 直接调用方法 B（this.methodB()），此时 this 是原始对象，不是代理对象，AOP 不会生效。
    • 解决：通过 AopContext.currentProxy() 或注入自身代理对象调用。
  2. 方法不是 public：Spring AOP 无法代理 private、protected、默认访问修饰符的方法。
  3. 类没有被 Spring 管理：必须让目标类成为 Spring Bean。
  4. 代理方式不匹配：如果使用 JDK 动态代理，而调用的是接口外的方法，增强不会生效。
  5. 异常被吞掉：@AfterThrowing 只有在方法抛出异常时才执行，如果异常被 catch 且未重新抛出，则不会触发。

Spring AOP vs AspectJ

对比维度 Spring AOP AspectJ
织入方式 运行时动态代理（无需修改字节码） 编译期或类加载期织入
连接点 仅方法执行 方法调用、字段访问、构造器等
性能 代理反射调用，略低 直接修改字节码，较高
依赖 Spring 内置 需额外依赖和编译插件
使用复杂度 简单，注解配置 复杂，需学习 AspectJ 语法

Spring 事务

Spring 事务管理是 Spring 框架最重要的企业级特性之一，它基于 AOP 实现，提供了声明式和编程式两种事务管理方式，其中声明式事务（@Transactional）使用最为广泛。

Spring事务管理类型

① 编程式事务

通过 TransactionTemplate 或 PlatformTransactionManager 手动控制事务提交和回滚，代码侵入性强，不推荐。

② 声明式事务（推荐）

使用 @Transactional 注解，基于 AOP 代理自动管理事务，代码简洁，低侵入。

@Transactional注解常用属性

属性 说明 默认值
propagation 事务传播行为 REQUIRED
rollbackFor 触发回滚的异常类型 RuntimeException 和 Error
noRollbackFor 不触发回滚的异常类型 无
isolation 事务隔离级别 DEFAULT（使用数据库默认）
timeout 事务超时时间（秒） -1（不超时）
readOnly 是否只读事务 false

事务传播行为

传播行为 说明
REQUIRED（默认） 有事务就加入，没有就新建。最常用
REQUIRES_NEW 总是新建事务，若当前存在事务则挂起它
SUPPORTS 有事务就加入，没有就以非事务执行
NOT_SUPPORTED 以非事务执行，若存在事务则挂起
MANDATORY 必须在事务中执行，否则抛异常
NEVER 必须非事务执行，若存在事务则抛异常
NESTED 如果当前有事务，则嵌套事务（保存点），否则新建事务

REQUIRED（默认）

  • 规则：有事务就加入，没有就新建。
  • 场景：methodA 调用 methodB，两个方法都使用 REQUIRED。
  • 结果：methodB 加入 methodA 的事务。它们共用一个事务，任何一方回滚都会导致整个事务回滚。最常用，保证数据一致性。

REQUIRES_NEW

  • 规则：总是新建事务，挂起当前事务。
  • 场景：methodA 调用 methodB，methodB 使用 REQUIRES_NEW。
  • 结果：methodB 开启新事务，与 methodA 的事务互不影响。methodB 成功提交后，即使 methodA 后续回滚，methodB 的数据也不会回滚。常用于需要独立提交的场景，如记录日志。

常见事务失效场景

  1. 同类内部方法调用：this.methodB() 调用同类中标注 @Transactional 的方法，由于 this 不是代理对象，AOP 拦截失效。
    • 解决：通过 AopContext.currentProxy() 调用，或注入自身代理对象，或拆分到不同 Bean。
  2. 方法不是 public：@Transactional 只能代理 public 方法，private/protected 无效。
  3. 异常被捕获未抛出：事务方法内部 try-catch 吞掉异常，事务管理器感知不到异常，不会回滚。
    • 解决：catch 中手动回滚 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly(); 或重新抛出异常。
  4. rollbackFor 未指定检查异常：默认只回滚运行时异常，Checked Exception 不会回滚。
  5. 数据库引擎不支持事务：MyISAM 不支持事务，需使用 InnoDB。
  6. 类未被 Spring 管理：目标对象不是 Spring Bean。
  7. 多线程调用：@Transactional 方法内部新启动线程，新线程不在事务范围内。
  8. 传播行为使用不当：例如 NOT_SUPPORTED 或 NEVER 导致事务未生效。

Spring MVC

Spring MVC 是 Spring 框架中用于构建 Web 应用程序的模块，基于 MVC 设计模式，提供了灵活、松耦合的 Web 开发方式。

MVC设计模式

  • Model（模型）：承载数据，通常是 POJO、Service 层返回的数据。
  • View（视图）：展示数据，JSP、Thymeleaf、FreeMarker 等。
  • Controller（控制器）：处理用户请求，调用业务逻辑，返回模型和视图。

Spring MVC 围绕 DispatcherServlet 设计，它作为前端控制器统一接收请求并分发给相应的处理器。

工作流程

流程说明（重要）：

  1. 客户端（浏览器）发送请求， DispatcherServlet拦截请求。
  2. DispatcherServlet 根据请求信息调用 HandlerMapping 。HandlerMapping 根据 URL 去匹配查找能处理的 Handler（也就是我们平常说的 Controller 控制器） ，并会将请求涉及到的拦截器和 Handler 一起封装。
  3. DispatcherServlet 调用 HandlerAdapter适配器执行 Handler 。
  4. Handler 完成对用户请求的处理后，会返回一个 ModelAndView 对象给DispatcherServlet，ModelAndView 顾名思义，包含了数据模型以及相应的视图的信息。Model 是返回的数据对象，View 是个逻辑上的 View。
  5. ViewResolver 会根据逻辑 View 查找实际的 View。
  6. DispaterServlet 把返回的 Model 传给 View（视图渲染）。
  7. 把 View 返回给请求者（浏览器）

拦截请求

-> 处理请求(HandlerMapping、HandlerAdapt、Handler)

-> 渲染视图 (ViewResolver、Model->View)

-> 返回视图

上述流程是传统开发模式（JSP，Thymeleaf 等）的工作原理。然而现在主流的开发方式是前后端分离，这种情况下 Spring MVC 的 View 概念发生了一些变化。由于 View 通常由前端框架（Vue, React 等）来处理，后端不再负责渲染页面，而是只负责提供数据，因此：

  • 前后端分离时，后端通常不再返回具体的视图，而是返回纯数据（通常是 JSON 格式），由前端负责渲染和展示。
  • View 的部分在前后端分离的场景下往往不需要设置，Spring MVC 的控制器方法只需要返回数据，不再返回 ModelAndView，而是直接返回数据，Spring 会自动将其转换为 JSON 格式。相应的，ViewResolver 也将不再被使用。

怎么做到呢？

  • 使用 @RestController 注解代替传统的 @Controller 注解，这样所有方法默认会返回 JSON 格式的数据，而不是试图解析视图。
  • 如果你使用的是 @Controller，可以结合 @ResponseBody 注解来返回 JSON。

常用注解

注解 说明
@Controller 标识一个类为控制器，通常配合 @RequestMapping 使用
@RestController 等于 @Controller + @ResponseBody，方法返回数据直接写入响应体
@RequestMapping 映射请求 URL 和 HTTP 方法，可标注在类和方法上
@GetMapping / @PostMapping / @PutMapping / @DeleteMapping / @PatchMapping 更具体的请求方法映射，简化书写
@RequestParam 获取请求参数（query 或 form 数据）
@PathVariable 获取 URL 路径变量，如 /user/{id}
@RequestBody 获取请求体，通常用于接收 JSON 数据
@ResponseBody 将方法返回对象序列化为响应体（JSON/XML）
@ModelAttribute 从请求参数、表单或 Model 中绑定对象
@RequestHeader 获取请求头信息
@CookieValue 获取 Cookie 值
@SessionAttribute 从 Session 中获取属性
@ExceptionHandler 在控制器内处理异常，可定义在 @ControllerAdvice 中

异常处理

三种方式：

  1. 局部异常处理：在 Controller 内使用 @ExceptionHandler 方法。
  2. 全局异常处理：使用 @ControllerAdvice + @ExceptionHandler，拦截所有 Controller 的异常。
  3. 实现 HandlerExceptionResolver：自定义异常解析器，更底层灵活。

@ControllerAdvice 是推荐方式，可配合 @ResponseStatus 和返回 ResponseEntity 统一响应格式。

RESTful支持

Spring MVC 天然支持 RESTful 风格：

  • 使用 HTTP 方法表示操作：GET 查询、POST 创建、PUT 更新、DELETE 删除。
  • 使用 URL 表示资源：/users/1。
  • @PathVariable 提取路径参数，@RequestBody 接收 JSON。
  • 内容协商：根据请求头 Accept 返回 JSON、XML 等格式。

过滤器和拦截器

维度 过滤器（Filter） 拦截器（Interceptor）
规范 Servlet 规范 Spring MVC 框架
执行顺序 在 DispatcherServlet 之前 在 DispatcherServlet 之后，Controller 方法之前
作用范围 所有请求（包括静态资源） 仅 Spring MVC 处理的请求
能否修改请求/响应 可以（如设置编码、添加头） 较难直接修改响应，但可修改 ModelAndView
能否获取处理方法信息 不能 可以（HandlerMethod、方法参数、注解等）
依赖注入 通常需要手动获取 Spring 容器中的 Bean（也可以使用代理） 天然支持 Spring 依赖注入
实现方式 基于回调函数 基于 Java 反射（动态代理）
典型场景 编码、跨域、安全过滤 权限、日志、性能监控

Spring Boot

pring Boot 是基于 Spring 框架的快速开发脚手架，它的核心设计目标是简化 Spring 应用的搭建和配置。通过“约定优于配置”的理念，让开发者能够快速创建独立、生产级别的 Spring 应用。Spring Boot 的核心是自动配置 + Starter + 内嵌容器，掌握这三者及启动流程，就能应对大多数面试场景。

核心特性

  • 自动配置：根据类路径依赖自动配置 Spring 应用（如引入了 spring-boot-starter-web 就自动配置 MVC、Tomcat）。
  • 起步依赖：spring-boot-starter-* 一站式引入相关依赖，避免版本冲突。
  • 内嵌服务器：默认 Tomcat，可切换 Jetty/Undertow，直接运行 JAR，无需外置容器。
  • 生产就绪：Actuator 提供健康检查、指标、日志等监控端点。
  • 无代码生成、无 XML：全部用注解和 Java 配置。

核心注解与启动

@SpringBootApplication 是一个组合注解，包含：

  • @SpringBootConfiguration：标识当前类为配置类。
  • @EnableAutoConfiguration：开启自动配置。
  • @ComponentScan：扫描当前包及子包的组件。

自动装配原理

自动装配是 Spring Boot 最核心的机制，通过条件化配置，根据类路径和已存在的 Bean 自动创建所需组件。

核心流程：

  1. 获取所有自动配置类候选：@EnableAutoConfiguration导入选择器AutoConfigurationImportSelector，选择器读取文件AutoConfiguration.imports获取所有候选的配置类
  2. 条件过滤：使用各种 @ConditionalOnXxx 条件注解进行过滤
  3. 注册为Bean：过滤后的配置类会被注册为 Bean 定义，由 Spring 容器管理

Stater机制

Starter 是一组依赖描述符，将某个功能所需的依赖和自动配置打包在一起。

命名规范：

  • 官方 Starter：spring-boot-starter-*（如 spring-boot-starter-web）。
  • 自定义 Starter：*-spring-boot-starter。

原理：Starter 本身不包含代码，只是管理依赖；真正干活的是自动配置类，通过条件注解在合适的条件下生效。

配置管理

Spring Boot 支持多种配置来源，优先级从高到低通常为：

命令行参数 > 环境变量 > 配置文件（application.yml / application.properties）> 默认配置。

  • 多环境配置：通过 spring.profiles.active 激活不同 profile。
    • application-dev.yml、application-prod.yml 等。
  • 配置绑定：
    • @Value("${key}")：简单值注入。
    • @ConfigurationProperties(prefix = "app")：类型安全的绑定，支持松散绑定。
  • 随机值与占位符：${random.uuid}、${server.port} 等。

内嵌服务器

Spring Boot 默认使用内嵌 Tomcat，可通过依赖替换为 Jetty 或 Undertow。

  • 优势：应用打包为 jar 文件，直接 java -jar 运行，无需外部服务器。
  • 配置：server.port、server.servlet.context-path、server.tomcat.* 等。
  • 优雅停机：server.shutdown=graceful 并配合 spring.lifecycle.timeout-per-shutdown-phase。
