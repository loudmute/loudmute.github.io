Object

java.lang.Object是所有类的的根父类。不写extends，也默认继承它。

Object有很多方法，也就是所有类的通用方法，比较重要的有：

== 和 equals()

==用于比较基本数据类型和引用类型的变量：

  • 对于基本数据类型，==比较的是值是否相等
  • 对于引用数据类型，==比较的是引用指向的对象是否相同

实际上，==比较的都是值，只不过引用变量的值虽然用于标识指向的对象，但是Java语言不将其定义为可见的物理内存地址。

equals()只用于比较引用类型的变量，而所有引用类型都是Object的子类，都具有equals方法。

  • 类没有重写equals()，比较的是对象是否相同，即默认的Object的equals()方法
  • 类重写了equals()，比较的一般是对象的内容是否相等，即重写方法的逻辑

hashCode()方法

hashCode()方法，是为了对象可能作为哈希表中的key而准备的，使用hashCode()方法计算出对象对应的哈希值，大大缩减了哈希表的查找范围，提升了查找效率。

hashCode()计算哈希值：

  • Object默认的hashCode()：根据对象身份(和对象的内存地址有关)，不看字段内容；
  • 重写后的hashCode()：根据重写后的equals()方法用到的字段，String中是对每个字符累加:h = 31 * h + char[i]

哈希表

哈希表的结构是由数组和联表/树组成的，每个数组的元素可能是null或者跟着一个链表/树，称之为一个桶，桶中的每个节点存着键值对<key，value> ，并且key是唯一的。

这里的key唯一取决于key对象的equals方法：

若是比较对象相同，则key的对象唯一

若是比较对象内容相等，则key的内容唯一

根据一个key，找到哈希表中对应的键值对<key, value>的过程如下：

1）key通过hashCode()方法转化为哈希值，再简单转换为数组对应的下标，找到对应的桶；

2）key通过equals()方法与桶中的节点的key比较，最终找到对应的键值对。

为什么重写equlas()方法，也要重写hashCode()方法？

因为重写之前，hashCode()方法是根据对象身份计算哈希值的，如果重写equals()方法比较的是两个对象的内容，不重写hashCode()则会因为两个对象不相同导致哈希值不同，在哈希表查找过程的第一步往往就会进错桶（除非哈希碰撞），也就无法比较两个对象的内容。

是什么

String是不可变的字符序列：

  • final class不可被继承
  • 内部是private final数组（jdk8及以前多为char[]；jdk9及以后多为byte[]+编码标记）
  • 实现了java.io.Serializable, Comparable<String>, CharSequence等类

一旦修改，对象不再改变，看起来像改变的操作，都是返回了新的String对象。

为什么不可变

设计意图：

String 被设计为不可变，主要解决了四个核心问题。

第一，安全性。 字符串广泛承载敏感信息，比如文件路径、数据库连接串、类名、权限标识。如果可变，这些关键值就可能被篡改，导致安全漏洞。不可变天然形成了一道安全屏障。

第二，线程安全。 不可变对象状态永不改变，多线程并发读写完全不需要加锁，这是并发编程里最理想的安全模式。

第三，字符串常量池的共享。 常量池依赖不可变性来复用相同字面量。如果可变，一个引用修改内容，所有共享该对象的引用都会被污染，常量池就失去了意义。

第四，作为 HashMap 键的可靠性。 String 是最常用的 Map key，它的哈希值一旦计算就被缓存，内容不变则哈希值永远稳定。如果可变，存入 Map 后改了内容，哈希值就变了，会导致数据丢失、查找失败。

这四个原因叠加，让 String 的不可变性成为整个 Java 平台安全与性能的基石。

源码实现：

  1. 内部数组是private final的，并且String没有提供修改的方法

  2. String类是final的，避免了子类继承破坏约定

字符串常量池

字符串常量池（String Constant Pool）主要解决的是避免重复创建相同内容的字符串对象，从而节省内存并提高性能的问题，其存在于JVM的堆内存中。

字符串常量池在底层实现上是一个StringTable，本质上是一个哈希表，将字符串字面量（编译时期代码中的双引号中的字符串）映射到String对象引用地址，比如上述代码过程中的<"abc"，对象B的引用地址>

当通过字面量重复创建字符串对象时，会共享同一个字符串对象，通过new创建相同内容的字符串对象时，虽然会不会共享同一个字符串对象，但是相同内容的字符串对象共享同一个字符数组。

方法intern()

  • 返回值：总是返回常量池中该字符串对象的引用。
  • 执行逻辑：
    • 如果池里没有：把当前字符串对象的引用添加到池里，然后返回这个对象的引用。
    • 如果池里有：直接返回池里已有对象的引用。

拼接

把多个字符串（或与其他类型）连成一个新字符串。

因为 String 不可变，拼接往往意味着：准备内容 → 得到新的 String，而不是改原来的对象。

关键字”+”

  • 编译期能定死的常量：编译器直接合成一个字面量，如 "a"+"b" → "ab"，走常量池逻辑。
  • 有变量、在循环里：编译器一般变成 StringBuilder（或类似）的 append，再 toString()。
  • 循环里反复 s = s + xxx：每次循环仍可能新建 Builder / 中间字符串，效率差，应在循环外自己建一个 StringBuilder。

循环里 s = s + … 时，每一轮都是一次独立拼接，会反复产生新的字符串结果；在 Java 8 里这通常编译成每轮 new StringBuilder 再 toString，所以又慢又产生大量临时对象。JDK9+ 实现可能变，但「每轮重新拼一整份」的问题还在。因此大量拼接应自己维护一个 StringBuilder。

关键字”concat”

只能拼 String，null 会 NPE；实现上通常是复制到新数组再 new String。少量拼接可用，不如 + 灵活，大量拼接仍不如 Builder。

关键字”StringBuilder”（单线程首选）

内部是可变缓冲区，多次 append 改同一块（不够再扩容），最后一次性变成 String。 循环、大量拼接用它。

关键字”StringBuffer”（多线程）

和 Builder 用法几乎一样，但方法带 synchronized，线程安全、单线程更慢。 多线程共享同一个拼接器才考虑；现在更常见是线程内用 Builder，或用别的并发结构。

其他

  • String.join(".", "a", "b") → "a.b"
  • StringJoiner、Stream Collectors.joining 适合带分隔符的场景，底层仍多是 Builder。
