接口与实现类

框架

实现类

1. List（有序，可重复）

实现类 底层结构 特点 线程安全？
ArrayList Object[] 数组 随机访问快 O(1)，尾部插入快，中间插入/删除慢 O(n)，扩容1.5倍 否
LinkedList 双向链表 插入/删除快 O(1)，随机访问慢 O(n)，Deque操作可作栈/队列 否
Vector 数组 古老，方法用 synchronized 修饰，性能差 是
CopyOnWriteArrayList 数组，写时复制 读无锁，写全量复制，适合读多写极少 是
  • ArrayList 扩容：初始容量 10（JDK8），1.5 倍扩容，使用 Arrays.copyOf。
  • 快速失败：迭代时若结构被非迭代器自身修改，抛出 ConcurrentModificationException。CopyOnWriteArrayList 为弱一致性，无此异常。

2.Set（无序，不可重复）

实现类 底层结构 特点 线程安全？
HashSet 基于 HashMap，元素作为 key 无序，去重依赖 hashCode() + equals() 否
LinkedHashSet 继承 HashSet，底层 LinkedHashMap 有序（插入顺序），效率略低于HashSet 否
TreeSet 基于 TreeMap（红黑树） 自然排序或自定义比较器，O(log n) 否
  • 去重原理：底层 HashMap 的 key 唯一。需同时重写 hashCode() 和 equals()。

3.Queue（排队，用于缓冲/优先级）

  • PriorityQueue：二叉小顶堆，自然顺序或比较器，非线程安全。
  • ArrayDeque：循环数组实现的双端队列，可作栈/队列，比 LinkedList 快。
  • BlockingQueue：线程安全的阻塞队列，生产者-消费者模式核心（ArrayBlockingQueue 有界数组，LinkedBlockingQueue 有界链表，SynchronousQueue 无缓冲）。

4.Map（键值对）

实现类 底层 排序 null 键值 线程安全
HashMap 数组+链表/红黑树 无 允许 1 个 null 键，多 null 值 否
LinkedHashMap 继承 HashMap，增加双向链表 插入顺序 / 访问顺序（LRU） 同 HashMap 否
TreeMap 红黑树 自然排序或比较器 键不能为 null 否
Hashtable 数组+链表（古老） 无 均不可为 null 是（全表锁）
ConcurrentHashMap JDK7 分段锁；JDK8 同 HashMap + CAS+synchronized 锁桶头 无 均不可为 null 是

  • 为什么 ConcurrentHashMap 的 key/value 不能为 null：并发环境下，get() 返回 null 无法区分是“不存在”还是“存了 null 值”，存在二义性。

  • IdentityHashMap：key 比较用 == 而非 equals()，用于序列化等特殊场景。

  • WeakHashMap：Entry 的 key 为弱引用，GC 后自动删除，可用于缓存。

ArrayList/LinkedList

底层数据结构

  • ArrayList：基于动态数组 Object[]。内存上是连续空间，支持通过下标快速访问（RandomAccess）。
  • LinkedList：基于双向链表。每个节点（Node）存储了元素值和前后指针，内存空间不连续。

核心性能对比

操作 ArrayList LinkedList 说明
随机访问 get/set O(1) O(n) ArrayList 直接通过下标定位；LinkedList 需从两端遍历
头插入/删除 O(n) O(1) ArrayList 需要整体移动后面元素；LinkedList 只需改指针
尾插入/删除 O(1) (均摊) O(1) ArrayList 扩容时会偶现 O(n)，但均摊下来是 O(1)
中间插入/删除 O(n) O(1) (定位时间另算) LinkedList 只需改指针，但寻找插入位置仍需 O(n)，总体 O(n)
内存占用 仅存元素和少量数组头信息 每个节点额外存前后指针，内存开销大 –

ArrayList的扩容机制

  • 初始容量：JDK8 中是空数组，第一次添加元素时才初始化，默认容量为 10。
  • 扩容时机：当 size == elementData.length 时触发，确保容量足够。
  • 扩容大小：通常是 1.5 倍（oldCapacity + (oldCapacity >> 1)）。
  • 扩容过程：创建新长度的数组，通过 Arrays.copyOf() 将旧数组元素浅拷贝到新数组。

细节：

  • 若通过 addAll 一次性添加大量元素，会触发一次足够大的扩容，避免多次扩容。
  • 可以用 ensureCapacity(int minCapacity) 提前预分配容量，减少扩容次数。
  • 扩容是潜在的性能消耗点，如果能预估数据量，最好在构造时指定初始容量。

适用场景

  • ArrayList：随机访问多、尾部追加多、能预估容量。典型场景：数据读取展示、缓存列表、批量处理。
  • LinkedList：头尾插入删除频繁（如实现队列、栈）、对内存占用不敏感。典型场景：生产者消费者缓冲区、LRU 缓存（利用链表的快速增删）。

实际开发中优先考虑 ArrayList，因为它内存连续，CPU 缓存友好，且大多数场景下尾部操作居多。只有当你明确需要频繁在头部或中间插入/删除时，才用 LinkedList。

HashMap

底层数据结构

  • JDK 1.7：数组 (Entry[]) + 单向链表。
  • JDK 1.8 及以后：数组 (Node[]) + 链表 + 红黑树。

红黑树转换条件：链表长度 >= 8 且 数组长度 >= 64 时，链表转为红黑树；当树节点数 <= 6 时退化为链表。链表长度 ≥ 8：触发树化判断，数组长度 ≥ 64：真正执行树化。

Node 节点结构：

关键参数与初始化

容量（Capacity）：指内部维度的数组的长度，即桶的数量，默认为16

负载因子（loadFactor）：默认0.75

大小（Size）：实际存储的键值对个数

树化条件：链表长度 >= 8 且 数组长度 >= 64，数组长度不到优先考虑扩容

扩容条件：size > capacity * loadFactor 或者 链表长度 >= 8且数组长度<64

为什么容量必须是 2 的幂？

为了快速定位桶下标：index = (n - 1) & hash，代替 % 取模运算，位运算效率高。扩容后元素要么在原位置，要么在 原位置 + 原容量。

JDK8 的延迟初始化：构造时只设置参数，第一次 put 时才创建数组，节省内存。

核心方法原理

put 流程

  1. 计算 key 的 hashCode()，高 16 位异或低 16 位（扰动函数），减少碰撞。
  2. 数组未初始化则调用 resize() 初始化。
  3. (n - 1) & hash 定位桶下标。
  4. 若桶为空：直接 newNode 插入。
  5. 若桶非空：
    • 第一个节点 key 相同 → 直接覆盖 value。
    • 是红黑树 → 调用树的插入方法。
    • 是链表 → 遍历链表，发现相同 key 则覆盖；若到末尾插入新节点（尾插法），插入后长度 >= 8 则树化。
  6. ++size 若超过阈值，执行 resize() 扩容。

get 流程

  1. 计算 key 的 hash，定位桶下标。
  2. 检查桶第一个节点：key 相等直接返回。
  3. 否则，红黑树则调用 getTreeNode，链表则遍历查找。
  4. 找不到返回 null。

resize扩容（2倍）

  1. 创建 2 倍容量新数组。
  2. 遍历旧数组每个桶：单个节点直接重新计算下标放入；链表拆分成低位链（留在原下标）和高位链（原下标 + 原容量）；红黑树按同样方式拆分。
  3. JDK8 可避免 JDK7 头插法的死循环问题（采用尾插法）。

线程安全问题

  • HashMap 线程不安全：
    • JDK7：扩容头插法可能导致环形链表，引发 get 死循环（CPU 100%）。
    • JDK8：改尾插法避免死循环，但仍有数据覆盖、size 不准确等问题。
  • 解决方案：使用 ConcurrentHashMap 或 Collections.synchronizedMap。

hashCode/equals与元素约束

在 Java 集合中，equals() 和 hashCode() 是保证元素正确存储、查找和去重的基石，它们与元素约束一起，决定了集合的行为是否符合预期。

核心概念

  • equals()：定义两个对象是否“逻辑相等”。在 Object 中默认是 ==（比较引用地址）。
  • hashCode()：返回对象的哈希码，用于快速定位桶位置。默认是本地方法，通常返回对象地址的整数形式。

两者在哈希表（HashMap、HashSet、Hashtable）中协同工作：

  1. 先用 hashCode() 定位桶。
  2. 再用 equals() 判断桶内的对象是否真正相同。

必须遵守的契约

  1. 自反性、对称性、传递性、一致性（equals 规范）。
  2. 如果两个对象 equals 相等，则 hashCode 必须相等（强制）。
  3. 如果两个对象 equals 不等，hashCode 尽量不同（非强制，但影响性能）。

违反契约的直接后果：

  • equals 相等但 hashCode 不同 → 哈希表中会产生两个相同的“键”，get 找不到正确的值。
  • 存入集合后修改参与 hashCode/equals 的字段 → 对象“丢失”，无法删除或查找，导致内存泄漏

不同集合对元素的约束

  1. HashSet / HashMap 的键
  • 依赖：hashCode() + equals()。
  • 约束：
    • 作为键/元素的类必须正确重写 hashCode() 和 equals()。
    • 键对象最好是不可变的（如 String、Integer），否则放入后修改会影响哈希值和位置。
  1. TreeSet / TreeMap 的键
  • 依赖：Comparable 接口的 compareTo() 或构造时传入的 Comparator。
  • 约束：
    • 元素必须实现 Comparable，或创建集合时提供 Comparator。
    • compareTo 返回 0 时视为相等，会覆盖旧值（即使 equals 返回 false）。
    • 必须保证 compareTo 与 equals 一致（推荐），否则可能违背 Set/Map 的“不重复”语义。
  1. LinkedHashSet / LinkedHashMap
  • 继承哈希集合特性，同时维护双向链表记录插入/访问顺序。
  • 约束同 HashSet/HashMap。
  1. ArrayList / LinkedList
  • 只依赖 equals()（在 indexOf、contains、remove 等操作时）。
  • 不依赖 hashCode()，但重写 equals 仍然建议同时重写 hashCode，保持契约。

遍历与fail-fast

在 Java 集合中，遍历时如果发现集合被意外修改，会立即抛出 ConcurrentModificationException，这就是 fail-fast（快速失败）机制。它的目的是尽早暴露并发修改问题，避免程序在不确定的状态下继续运行。

fail-fast 的原理

每个集合内部都有一个 modCount 字段，记录集合结构被修改的次数（增删元素、扩容等，set 不增加）。

创建迭代器时，迭代器会记住这个 modCount 值，存为 expectedModCount。每次调用 next()、remove() 等方法时，迭代器都会检查 modCount 是否等于 expectedModCount：

  • 若不等 → 立即抛出 ConcurrentModificationException。
  • 若相等 → 继续执行。

典型的 fail-fast 场景

  1. 单线程中直接修改集合

在增强 for 循环或迭代器遍历时，使用集合的 add/remove 方法直接修改集合结构，会触发 fail-fast。

因为增强 for 底层就是迭代器，list.remove 修改了 modCount，而迭代器的 expectedModCount 没变。

  1. 多线程并发修改

一个线程在遍历，另一个线程修改了集合结构。

如何安全地在遍历时修改集合？

  1. 使用迭代器的 remove() 方法

Iterator.remove() 内部会同步 expectedModCount = modCount。

  1. 使用常规 for 循环并手动控制索引
  1. 使用并发集合（fail-safe）

如 CopyOnWriteArrayList、ConcurrentHashMap，它们不会抛出 ConcurrentModificationException。
