JVM 基础这块，可以按一条主线串：

Java 怎么跑起来 → 跑的时候内存怎么分 → 对象怎么进堆、怎么被回收 → 类怎么加载进来 → 出了内存问题怎么认。

脉络：

JVM基本概念

JVM vs JRE VS JDK

JVM（Java Virtual Machine）是运行Java字节码的虚拟机，输入是符合JVM规范的字节码（常见.class文件形式），输出是程序运行的结果。JVM根据不同的系统有不同的实现，以达到输入相同的字节码、输出相同的程序运行的结果，即”一次编译，到处运行”。

JRE（Java Runtime Environment）是运行已编译Java程序所需要的环境，主要包括两个部分：1）JVM；2）Java Class Library：一组标准类库，提供常用的功能和API（如I/O操作、网络通信、数据结构等）。

JDK（Java Development Kit）是供开发者使用、用于编写和编译Java程序的Java开发工具包，包含JRE、编译器Javac以及其他工具。

字节码

字节码是Javac编译器生成、输入JVM的中间代码，以.class文件的形式存在、按照严格格式排列的二进制数据，既非可读的源码也非面向CPU的机器码、只面向JVM。

字节码的好处：结合了编译型语言”提前编译，严格检查”的效率和安全，以及解释性语言的”虚拟执行，动态灵活”的跨平台能力。

从源代码到执行过程

解释器：快速启动，逐条将字节码翻译成机器码并执行。

JIT(Just-in-time) 编译器：监控热点代码，在运行时将其编译为高度优化的本地机器码，后续直接执行。

融合了解释型语言的跨平台动态性和编译型语言的高峰值性能。

JVM运行时数据区

JVM运行时数据区即Java内存区域，有5个区域，按照线程私有/共享分为两种：

  • 线程私有：程序计数器，Java虚拟机栈，本地方法栈
  • 线程共享：方法区/元空间，堆区

堆区占用的内存，受到JVM的堆大小参数限制和GC的管理；并且在JDK1.8版本之前，方法区叫做”永久代”，和堆区是逻辑上分开但是物理上连续的内存块，也受到JVM堆大小参数限制，很容易因为类加载过多出现OutOfMemoryError。从JDK1.8版本开始，永久代移除，由方法区/元空间取代，直接在本地内存中分配，不受堆大小参数限制，不太容易出现OutOfMemoryError，排除了堆区出问题可能性问题定位也会更清晰。

程序计数器

程序计数器(Program Counter Register)用于标志当前线程所执行到的指令的位置。

操作系统分配不同的时间片，让CPU在不同线程之间来回切换，不同的线程执行不同的指令，当切换回当前线程后，通过程序计数器来知道上次指令执行到哪了。

唯一不会抛出OutOfMemoryError的区域。

Java虚拟机栈

Java虚拟机栈(Java Stack)是管理Java方法调用和执行的区域。每个方法被执行的时候，JVM都会创建一个栈帧，一个方法从调用到结束，就对应着栈帧在Java虚拟机栈中入栈到出栈。

栈帧的组成：

  • 局部变量表：存放方法参数和方法内定义的局部变量。这是我们最常打交道的部分。
  • 操作数栈：一块用于计算的临时空间。比如做加法，先把两个数压入栈，再弹出进行加法运算，结果再压回栈。字节码的很多指令就是围绕这个栈操作的。
  • 动态连接：指向运行时常量池中该栈帧所属方法的引用。
  • 方法返回地址：方法执行完后该回到哪里继续执行。

异常:

  • 如果线程请求栈帧深度远大于虚拟机允许的深度，抛出StackOverflowError
  • 如果栈允许动态扩展但是申请不到足够内存，抛出OutOfMemoryError

本地方法栈

作用与虚拟机栈非常相似，区别是它为 Native 方法（非 Java 代码编写的方法）服务。

方法区

**方法区(Method Aread)/元空间(Meta Space)**存储类及类结构相关的信息，JVM每加载一个类，都会把类相关的结构信息放在方法区，之后创建对象、调用方法都要来这里查询。

方法区主要存储四类数据：

  1. 类的元信息

每个被加载的类，都会在这里存一份完整的结构描述：

  • 类的全限定名、访问修饰符
  • 直接父类和接口的列表
  • 字段信息（名称、类型、修饰符）
  • 方法信息（名称、返回值、参数、修饰符、字节码指令）

没有这部分信息，JVM 就不知道一个类有哪些字段和方法。

  1. 运行时常量池（核心）

这是方法区最活跃的部分。每个类的 .class 文件中都有一个静态常量池，类加载后，它就被放入方法区成为运行时常量池。里面主要存放：

  • 字面量：如文本字符串 "hello"、被声明为 final 的常量值。
  • 符号引用：类、方法、字段的全限定名、描述符，在类加载的“解析”阶段会被转换成直接引用。

运行时常量池具备动态性，程序运行时也可以向池里添加新的常量，如 String.intern() 方法。

  1. 静态变量

类中被 static 修饰的变量，它们属于类本身，不属于任何对象，所以被分配在方法区。

  1. 即时编译（JIT）代码缓存

JIT 编译器将热点方法编译成本地机器码后，这些机器码就缓存在这里，后续可直接执行。

堆区

**堆区(Heap Area)**存放对象实例和数组的区域，是JVM管理内存中最大、最核心的一块区域。

堆区存放的对象包含的信息：

  • 对象头：运行时元数据（哈希码、GC、锁状态），类型指针（指向对象所属类的元数据）
  • 实例数据：定义的成员变量（包括从父类继承的）的实际值
  • 对齐填充

堆区是垃圾收集器管理的主要区域，也称为”GC堆”：

  • 分代设计（经典要点）：为了优化垃圾回收，堆通常被划分为：
    • 新生代：新生的对象在这里。一次垃圾回收（Minor GC）就能回收掉大部分对象。新生代又分为 Eden 区和两个 Survivor 区（From/To），对象在它们之间按年龄流转。
    • 老年代：那些在新生代中熬过多次垃圾回收、生命周期较长的对象会被晋升到老年代。
  • 异常：当堆中没有足够内存完成实例分配，且也无法再扩展时，抛出 OutOfMemoryError。

对象创建

对象创建过程

JVM（HotSpot虚拟机）创建对象的过程如下：

  1. 类加载检查：虚拟机执行new指令时，先检查常量池中是否存在对应的符号引用，并检查该类是否已经加载、解析、初始化，若没有则先执行类加载过程。

指针碰撞 (Bump the Pointer)：堆内存规整（Serial、ParNew 等带压缩整理的收集器），空闲内存与已用内存之间有一指针，分配时指针移动。

空闲列表 (Free List)：堆内存不规整（CMS 等基于标记-清除的收集器），JVM 维护一个可用内存块的列表，分配时找一块足够大的。

CAS + 失败重试：保证原子性。

TLAB (Thread Local Allocation Buffer)：每个线程在 Eden 区预分配一小块私有缓冲区，优先在 TLAB 中分配，TLAB 用完再采用 CAS 方式分配新的 TLAB。可通过 -XX:+UseTLAB 开启（默认开启）。

  1. 分配对象内存：类加载通过后，根据类加载确定的对象大小从Java堆中划分内存。分配方式有”指针碰撞”和”空闲列表”;保证线程并发分配安全的方式有”CAS+失败重试”和”TLAB机制”。
  2. 初始化零值：将分配的内存空间(对象头除外)初始化为零值，使得Java代码中未赋值的实例字段可以使用对象类型的零值。
  3. 设置对象头：在对象头中记录类元数据信息、哈希码、GC分代年龄、锁状态等必要信息，具体设置依照虚拟机运行状态而定。
  4. 执行**<init>**方法：虚拟机视角下对象已创建，但仍需执行<init>方法按程序员定义初始化，最终完成对象创建。

对象访问方式

程序通过栈上的reference数据来操作具体对象，主流方式有句柄访问和直接指针访问两种。具体访问方式根据由虚拟机实现方式而定，HotSpot虚拟机采用的直接指针访问这种方式。

句柄访问：在堆中划分出一块句柄池，reference 存句柄地址，句柄包含 指向对象实例数据的指针 和 指向对象类型数据的指针。

优点：对象移动时，只改变句柄中的 指向对象实例数据的指针，reference不变。

缺点：多了一次指针定位的开销。

直接指针访问：reference 直接存对象实例地址，对象实例数据中包含 指向对象类型数据的指针。

优点：少了一次指针定位的开销。

缺点：对象移动时，reference也需要改变。

垃圾回收

参考连接：https://www.cnblogs.com/javastack/p/12521914.html

判断对象需要回收 -> 引用类型与回收策略 -> 垃圾回收算法 -> 分代 -> 垃圾收集器

**垃圾回收（Garbage Collection，GC）**是JVM中一套自动管理堆内存的机制。GC绝大多数发生在Java内存中的堆区，极少发生在方法区，当前主要讨论Java堆中的GC。GC需要考虑的问题有：哪些内存需要回收、如何回收、何时回收。

线程私有区域的内存，是“函数调用则生，函数返回则死”，其生命周期完全由方法的执行逻辑决定，是100%确定的。而GC要解决的是堆里“生得随机、死得随机”的共享对象。这是JVM内存管理中，最经典的两极分化。

判断对象需要回收

判断对象需要被回收，存在两种方法：1）引用计数算法；2）可达性分析算法

引用计数算法

给对象添加一个引用计数器，被引用时计数器加1，引用失效时计数器减1，计数器为0时对象死亡。

问题：当对象互相循环引用时，计数器永远不为0，无法释放对象内存。

可达性分析算法（HotSpot采用）

从一些列被称为”GC ROOTS”的跟对象出发，根据引用关系不断向下搜索，走过的路径叫做”引用链”。如果一个对象到任何GC ROOTS都没有引用链，那就是不可达的，需要回收。

可以做GC ROOTS的对象：

  • Java虚拟机栈中引用的对象
  • 本地方法栈中引用的对象
  • 方法区中常量引用的对象
  • 方法区中类静态属性引用的对象

引用类型与回收策略

Java提供了四种引用类型，由强到弱，回收的迫切程度也不同：

强引用(Strong Reference)：最普通常见的引用，类似 Object o = new Object()；只要存在，被引用对象不会被GC回收。

软引用(Soft Reference)：描述有用但非必需的对象；在系统内存不足发生OOM之前，被GC回收；适合做内存敏感的缓存。

弱引用(Weak Reference)：描述非必需对象；只能活到下次GC之前，无论内存是否充足；WeakHashMap中的键就是弱引用。

虚引用(Phantom Reference)：最弱，无法通过它获得对象实例；唯一目的就是对象被回收时获得一个系统通知。

垃圾回收算法

垃圾回收算法，主要包含四种算法：1）标记-清除算法；2）标记-复制算法；3）标记-整理算法；4）分代收集算法，它们不是互相割裂的，而是围绕内存的回收出现的问题不断递进的。

标记-清除算法

分标记和清除两个阶段，先标记需要回收的对象区域，再统一回收

缺点：1）执行效率不高（标记和清除的过程）；2）产生内存碎片，分配大对象时可能提前触发GC

标记-复制算法

可用内存分为相等的两块，每次只用一块；每次GC将存活对象复制到另一块区域，统一清除当前区域

优点：内存无碎片，实现简单、高效

缺点：内存浪费了一半

应用：商用JVM大多用它回收新生代。因为新生代对象98%都“朝生夕死”，不需要1：1划分，而是分一块较大的Eden和两块较小的Survivor，用Eden+一块Survivor复制到另一块Survivor，空间利用更优

标记-整理算法

标记后，让所有存活对象向内存一端移动，回收边界外的内存

优点：内存无碎片，无需浪费一半内存

缺点：移动对象需要STW(Stop-The-World)，并更新所有引用，比较耗时

应用：常用于老年代

STW（Stop-The-World） 是 JVM 在垃圾回收时必须执行的一个全局暂停动作：它会暂停所有的用户线程（应用代码），直到 GC 完成某些关键阶段，才会恢复执行。根本原因是为了保证对象引用关系的一致性。STW 就是为了获取一个“引用关系不变化”的静态快照，在这个快照上进行精确的标记和清理。

分代收集算法

当前JVM应用的基石：根据对象存活周期的不同，划分为新生代和老年代，分别采用各自合适的算法

新生代：大批对象死去，少量存活 -> 标记-复制算法

老年代：对象存活率高 -> 标记-清除或标记-整理算法

分代

根据”绝大多数对象朝生夕死，少数对象长期存活”的规律，JVM将堆中的区域划分为新生代和老年代，选择每个区域最合适的垃圾回收算法，以达到整体最优的GC效率。

为什么需要分代？

如果不分代，虚拟机每次 GC 都要对整个堆进行扫描和整理，效率极低。分代的好处在于：

  • 针对性回收：新生代对象死亡率高，可频繁回收，算法追求速度快；老年代对象存活率高，回收频率低，算法追求空间利用率。
  • 减少停顿范围：大部分 GC 只发生在新生代，停顿时间短，对应用影响小。
  • 提升吞吐量：把计算资源集中在“垃圾最多”的地方，避免全堆扫描。

分代区域划分

  1. 物理划分：新生代 vs 老年代
  • 新生代：占堆的 1/3 左右（可通过 -Xmn 设置）。再细分为：
    • Eden 区：默认占新生代 80%。绝大部分对象在这里诞生。
    • 两个 Survivor 区：From 和 To，各占 10%。用于保存经过一次 Minor GC 后存活的对象。
  • 老年代：占堆的 2/3 左右。存放经历多次 GC 仍存活的对象，以及大对象。
  • 元空间（方法区）：不在堆内，但有单独的 GC 逻辑（回收无用的类）。
  1. 逻辑划分：Eden : Survivor = 8 : 1 : 1 这个比例不是绝对，可通过 -XX:SurvivorRatio=8 调整。之所以这样设计，是因为新生代中 98% 的对象都熬不过第一次 GC，所以只需要很小的 Survivor 空间来容纳极少数存活对象。

分代的GC类型

分代下的对象流转

对象在新生代和老年代之间的“晋升”规则，是分代设计的核心控制逻辑：

  1. 对象优先在 Eden 分配 大多数情况，新对象诞生在 Eden。
  2. 大对象直接进入老年代 通过 -XX:PretenureSizeThreshold 设置阈值。因为大对象的复制成本高，而且可能让新生代内存提前吃紧。
  3. 长期存活对象晋升老年代 每个对象头里有一个 GC 分代年龄（4 bit，所以最大年龄为 15）。对象每在 Minor GC 中存活一次并被复制到 Survivor 区，年龄 +1。当年龄达到 MaxTenuringThreshold（默认 15）时，就晋升到老年代。
  4. 动态年龄判定 并不是必须到 15 岁才晋升。若 Survivor 空间中相同年龄的所有对象大小之和超过了 Survivor 空间的一半，那么年龄大于等于这个年龄的对象，会直接晋升老年代，无需等到最大年龄。这能防止 Survivor 空间被撑爆。
  5. 空间分配担保 Minor GC 前，JVM 会检查老年代最大可用连续空间，是否大于新生代所有对象的总空间或历次晋升到老年代的平均大小。
    1. 如果大于：安全的，执行 Minor GC。
    2. 如果小于：可能先触发一次 Full GC，为老年代腾出空间，再执行 Minor GC。这就是“担保失败”的风险点。

垃圾收集器

垃圾收集器是分代理论的执行者，每个收集器都有自己的定位和适用场景。从发展历程来看，收集器经历了 单线程 → 并行化 → 并发化 → 低延迟化 的演进。

收集器 作用区域 线程模式 与用户线程并发？ 追求目标
Serial 新生代 单线程 否 简单、低开销
ParNew 新生代 多线程并行 否 缩短 STW
Parallel Scavenge 新生代 多线程并行 否 高吞吐量
Serial Old 老年代 单线程 否 简单、低开销
Parallel Old 老年代 多线程并行 否 高吞吐量
CMS 老年代 多线程 部分并发 最短停顿时间
G1 整个堆 多线程 部分并发 可控停顿时间
ZGC 整个堆 多线程 几乎全程并发 亚毫秒级停顿

类加载

是什么

类加载就是JVM把.class文件中的二进制字节流，读入内存并转化为JVM可以直接使用的Java类的全过程。

类加载的过程包括：加载、链接（验证、准备、解析）、初始化。

类的生命周期通常为：加载、链接（验证、装备、解析）、初始化、使用、卸载。

类加载过程

加载:

1）通过类的全限定名，获取二进制字节流

2）在方法去区创建类元数据

3）在堆区创建Class对象，作为入口

链接(验证、准备、解析):

验证：校验字节流符合JVM规范，保证安全

准备：为静态变量分配内存并设置默认零值

static final 编译期常量可能已是目标值；准备阶段不是执行代码赋的初值，例如 static int a = 1; 在准备阶段是 0，到初始化才变成 1。

解析：把常量池的符号引用变为直接引用

初始化：

执行类构造器 <clinit>()，按照代码里的书写顺序，依次执行静态变量的显式赋值和静态代码块

触发初始化的典型时机（主动使用）：

  • new、访问/设置静态字段（非常量）、调用静态方法
  • 反射（某些操作）
  • 初始化子类时，父类会先初始化
  • 标为启动类的主类
  • ……

访问 static final 编译期常量，往往不会触发该类初始化（常考）。

类加载器

类加载器是类加载过程的核心组件，根据一个类的全限定名，找到并读取对应的二进制流，并交给JVM去生成对应的类。

类的唯一性：同一个类由不同加载器加载，在 JVM 里是不同的类（全限定名 + 加载器）。

VM 自带了三层类加载器，它们是典型的“父子”层级结构：

类加载器 负责加载的范围 特点
启动类加载器 (Bootstrap ClassLoader) <JAVA_HOME>/jre/lib 下的核心类库，如 rt.jar 里的 java.lang.String、java.util.List 等 由 C++ 实现，不是 Java 类，在 Java 代码中用 null 表示
扩展/平台类加载器 (Platform ClassLoader) JDK 9 前叫“扩展类加载器”，加载 <JAVA_HOME>/jre/lib/ext 下的类；JDK 9 后改名为平台类加载器，加载部分标准扩展模块 由 Java 实现
应用程序类加载器 (Application ClassLoader) 加载你写的代码，即 classpath 下的所有类 由 Java 实现，是 ClassLoader.getSystemClassLoader() 的返回值

这三者的父子关系是：启动类加载器 → 平台类加载器 → 应用程序类加载器

双亲委派

双亲委派是类加载器的核心机制，流程为：当一个类加载器收到加载请求时，不会立刻自己去加载，而先把请求委托给父加载器，一层层向上传递。知道当父类加载器找不到该类时，子类加载器才会自己去尝试加载。

目的：1）安全：避免核心类被覆盖；2）唯一：核心类使用由启动类加载器加载，避免多份

打破双亲委派的例子（知道名字即可）：SPI（JDBC 驱动等）、热部署、OSGi、Tomcat 里部分隔离——面试能说「有场景需要打破，如 SPI 要由应用加载器加载厂商实现」就够。
