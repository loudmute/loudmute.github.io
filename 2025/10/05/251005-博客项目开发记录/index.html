用户表: user_account

创建数据库时，一般选择：字符集-utf8mb4，排序规则-utf8mb4_general_ci

user_account:

user_id int auto_incre, nick_name varchar(50), email(100), password varchar(100), created_time timestamp

user_id使用整数还是字符串：前者性能高，可能出现分布式问题；后者性能低，但不会担心分布式问题；目前博客项目不会使用分布式架构，上线也只是租一个几十块的云服务器。最后决定user_id用int表示

created_time使用datetime还是timestamp：datetime，是存储日期字符串，不会随着时区而改变；timestamp，是日期先转为utc（世界统一时间）再转为时间戳，查询时根据当地时区变为对应的日期时间。我决定使用timestamp来进行表示。

关于String的一个用法

主表不应该持有从表的主键

在我的表设计中，article表持有article_id和content_id，article_content也持有article_id和content_id

这在插入新文章时，造成了id顺序问题。插入article时需要已知content_id，插入content时需要已知article_id，这造成了一种死锁。

分析一下，article_content强依赖于article存在，所以article是主表，article_content是其从表；在article中content_id是外键，在article_content中article_id是外键；外键的本质是我属于谁，表示一种从属关系；因此article表中的content_id外键是多余的。

文章分页问题

分析文章列表分页逻辑，定位问题所在。

分页问题主要出在 后端分页参数 和 前端 hasNext 判断，ArticleList.vue 本身只是展示，逻辑在各页面的 loadArticles 里。

  1. 后端：页码换算错误（最严重）

ArticleServiceImpl 里把 pageNo - 1 直接当作 SQL 的 offset，正确应为 (pageNo - 1) * pageSize。

​ List

articles = articleMapper.select(pageNo - 1, pageSize);

​ return new PageResult

(pageNo, pageSize, null, articles);

ArticleMapper.xml 里是 limit #{offset}, #{size}，例如 pageSize=10 时：

页码 当前 offset 实际应 skip 结果
第 1 页 0 0 正常
第 2 页 1 10 只跳过 1 条，与第 1 页大量重复
第 3 页 2 20 同样错误

同样写法还出现在：

  • selectListByCategory → selectByCategory / selectByPCategory
  • selectListByTagId → selectByTag

所以首页、子分类页、标签页翻页都会出现 数据重复、遗漏、页码对不上。

  1. 后端：父分类查询没有分页

选中 父分类 时走 selectByPCategory，SQL 没有 limit：

Service 虽传了 pageNo、pageSize，但 SQL 不生效 → 分类页选父分类时一次返回全部文章，分页无效。

  1. 后端：未返回总条数 total

PageResult 的 total 一直是 null：

​ return new PageResult

(pageNo, pageSize, null, articles);

前端无法根据总数判断是否还有下一页。

  1. 前端：hasNext 推断不准确

首页、分类页、标签页都用同一规则：

​ this.articles = result?.list || []

​ this.hasNext = this.articles.length === this.pageSize

（Categories.vue、Tags.vue 相同。）

含义是：本页条数等于 pageSize 就认为还有下一页。

问题在于：

  • 总条数恰好是 pageSize 的整数倍时，最后一页仍会显示可点的「下一页」，再点一次会得到空列表或重复数据（叠加后端 offset 错误会更乱）。
  • 未使用后端 total，在 total 为 null 时也只能用这种猜法，本身就不可靠。

ArticleList.vue 只负责根据传入的 hasNext 禁用/启用按钮，问题不在组件内部。

总结
位置 问题
后端 ArticleServiceImpl offset 应为 (pageNo-1)*pageSize，现为 pageNo-1
后端 ArticleMapper.xml selectByPCategory 缺少 limit，父分类无法分页
后端 PageResult total 恒为 null
前端 Home/Categories/Tags.vue 的 loadArticles hasNext = list.length === pageSize 在整除场景会多出一页

根因在后端 offset 和父分类无 limit；前端 hasNext 是次要问题，在后端修好后仍建议用 total 或「本页是否满页 + 是否还有数据」更严谨地判断。

反序列化与泛型擦除

一句话本质

Java 泛型是编译期特性，运行时会被擦除。 反序列化器只能看到”外面有什么”，看不到”里面应该是什么”。

来龙去脉

泛型擦除机制

为什么 List

能强转

关键：元素本身携带了完整的类型信息，Jackson 能还原回来。

为什么 PageResult

不行

关键：T是个占位符，运行时没有留下任何信息告诉 Jackson 该用什么类型。

涉及的知识点

知识点 说明
泛型擦除 Java 为了兼容旧版本，运行时抹掉泛型参数
序列化/反序列化 对象 ↔ JSON 的转换过程
TypeReference 利用匿名内部类在编译期捕获并保留泛型信息，绕过擦除
Jackson 的类型推断 遇到具体类能还原，遇到泛型占位符就无能为力

总结

TypeReference 的作用：在编译期偷偷把 PageResult<Article>这个完整类型信息记录下来，告诉 Jackson “这里的 T 其实是 Article”。

对应类型应该含无参构造器。

增加vo类的ArticleVo，包含Article和ArticleContent，并且包含List<Tag> tags，查看文章详情不用/article/view，而是用接口/article/articleDetail

发布和更新文章合并

接口/article/upload和/article/upload的相关Controller、Service的逻辑，统一使用/article/saveArticle接口下的Controller、Service的逻辑。ArticleServiceImpl，saveArticle区分插入新文章还是更新已有文章通过articleId是否为null区别，插入新文章时无需articleId和createdTime的参数值，更新文章时必须有articleId，剩余参数title、createdTime、categoryId、tagIds、file均为可选。

分类列表逻辑合并

接口/category/list、/category/pCategoryList、categoryByPId统一用接口/category/categoryList替换，pCategoryId为null时是list的功能，为0时是pCategoryList的功能，不为null不为0时是categoryByPId的功能。

分类插入逻辑合并

接口/category/insertPCategory和/category/insertCategoryWithPId，不再使用，统一用/category/insertCategory替换，参数pCategoryId为0时是insertPCategory的功能，不为null不为0时insertCategoryWithPId的功能。

反序列化与泛型擦除

一句话本质

Java 泛型是编译期特性，运行时会被擦除。 反序列化器只能看到”外面有什么”，看不到”里面应该是什么”。

来龙去脉

泛型擦除机制

为什么 List

能强转

关键：元素本身携带了完整的类型信息，Jackson 能还原回来。

为什么 PageResult

不行

关键：T是个占位符，运行时没有留下任何信息告诉 Jackson 该用什么类型。

涉及的知识点

知识点 说明
泛型擦除 Java 为了兼容旧版本，运行时抹掉泛型参数
序列化/反序列化 对象 ↔ JSON 的转换过程
TypeReference 利用匿名内部类在编译期捕获并保留泛型信息，绕过擦除
Jackson 的类型推断 遇到具体类能还原，遇到泛型占位符就无能为力

总结

TypeReference 的作用：在编译期偷偷把 PageResult<Article>这个完整类型信息记录下来，告诉 Jackson “这里的 T 其实是 Article”。

对应类型应该含无参构造器。
