多线程基础

进程和线程

进程 线程
是什么 资源分配的基本单位（独立内存空间） CPU 调度的基本单位（依附进程）
内存 进程间一般隔离 同进程线程共享堆、方法区；各有栈、PC
开销 创建/切换更重 更轻
关系 一个进程可有多个线程 线程崩溃可能拖垮进程（视情况）

并发和并行

  • 并发（Concurrency）：同一时间段内多个任务交替推进（单核也能并发，靠时间片）。
  • 并行（Parallelism）：同一时刻多个任务真正一起跑（多核）。

线程的生命周期

线程的创建

关键类和接口：

  • 定义任务：

    • Runnable接口（无返回值，不抛出受检异常）

    • Callable接口（有返回值，抛出受检异常）

  • 执行任务：

    • Thread类（只接收Runnable的任务，不接收Callable的任务，因此有了FutureTask）

    • Execute接口（execute()方法执行Runnable的任务）

    • ExecuteService接口（继承自Execute接口，增加了submit()方法接收Callable的任务

  • 接收结果：Future接口，接收Callable定义的任务的返回结果

  • FutureTask：实现Runnable接口和Future接口，可以包装Callable定义的任务、送入Thread执行、并接收返回的结果

线程安全与同步

线程安全性问题

线程安全是Java并发的核心问题，它的根源来自Java内存模型(JMM)带来的可见性、有序性问题，以及多线程交错执行导致的原子性问题，这也是线程安全的三大特性：原子性、可见性、有序性；

Java内存模型（JMM）

JMM规定了线程和内存之前的抽象关系：

  • 主内存：所有线程共享的内存区域，存放实例字段、静态字段等
  • 工作内存：每个线程私有的内存区域，持有主内存中变量的副本

所有线程对变量的操作（读、写）必须在工作内存中，不能直接读写主内存；不同线程之间也无法直接访问对方工作内存中的数据，必须通过主内存来传递。

这种抽象直接导致了可见性问题：线程 A 修改了变量，线程 B 不能立刻看到。此外，编译器和处理器可能对指令重排，导致多线程下执行顺序与预期不符，这是有序性问题。再加上线程交错执行导致的原子性问题，三者共同构成线程不安全的三大源头。

线程安全的三大特性

特性 定义 保障手段
原子性 一个或多个操作，要么都执行不被中断，要么都不执行 synchronized、Lock、java.util.concurrent.atomic 的 CAS
可见性 一个线程对共享变量的修改，其他线程能够看到 volatile、synchronized、Lock、final
有序性 程序执行的顺序按照代码的先后顺序执行（禁止指令重排） volatile、synchronized、Lock、happens-before 原则

happens-before原则

这是JMM给出的判断数据是否竞争、线程是否安全的依据。如果 操作A happens-before 操作B，那么A的结果对B就是可见的，且A的执行顺序在B之前。

主要规则有：

  • 程序次序规则：一个线程内，按照代码顺序，前面的操作 happens-before 后面的操作。
  • volatile变量规则：对一个 volatile 域的写，happens-before 任意后续对这个 volatile 域的读。
  • 锁规则：对一个锁的解锁 happens-before 随后对这个锁的加锁。
  • 传递性：如果 A happens-before B，B happens-before C，那么 A happens-before C。
  • 线程start()/join()原则：线程的 start() happens-before 该线程的每个动作；线程所有动作 happens-before 另一线程的 join() 返回。

线程的同步方法

为了确保多个线程访问共享数据时的安全性，有一些常用的线程同步方法。

从语法层面上看，最基础的方法是使用synchronized、volatile关键字。此外JUC工具中，常用的还有的ReentrantLock、Atomic原子类等，还有ThreadLocal等。

synchronized和ReentrantLock都是对共享对象加互斥锁以确保线程安全，volatile不保证原子性，Atomic原子类属于乐观锁思想并保证单个变量的线程安全。

ThreadLocal

ThreadLocal 是 Java 实现线程封闭的核心工具。它另辟蹊径解决并发问题：不为共享变量加锁，而是为每个线程都创建一份变量的独立副本，从根源上避免竞争。它位于 java.lang 包下，是 Java 核心语言包的基础类。

核心原理

每个 Thread 对象内部都持有一个 ThreadLocalMap 类型的成员变量 threadLocals。这个 Map 以 ThreadLocal 对象为 key，以变量的线程私有副本为 value。

当调用 ThreadLocal.get() 时：

  1. 获取当前线程的 ThreadLocalMap。
  2. 以当前 ThreadLocal 实例为 key 查找对应的 value。
  3. 若找不到，调用 initialValue() 生成初始值并放入 Map。

内存泄漏

内存泄漏原因：

  • ThreadLocalMap 的 key 是弱引用，被 GC 回收后变成 null。
  • 但 value 仍是强引用，只要当前线程还存活（尤其是在线程池中线程会长期存活），这个 value 就永远不会被回收，造成内存泄漏。

ThreadLocal 的自我清理机制：

在 get()、set()、remove() 操作时，ThreadLocalMap 会顺带清理 key 为 null 的过期条目（expunge stale entries），一定程度上缓解了问题。

最佳实践：每次使用完 ThreadLocal 后，必须在 finally 块中调用 remove() 手动清除，避免在线程池复用线程时出现脏数据或内存泄漏。

死锁

死锁及常见场景的解决方法

死锁就是两个或多个线程相互等待对方释放资源，形成僵局，谁都无法继续执行。它的根源在于资源竞争。

产生死锁的必要条件：

  • 互斥：资源一次只能被一个线程使用。
  • 持有并等待：线程已经持有一个资源，还在等待别的资源，同时不释放手上的资源。
  • 不可剥夺：资源不能被强制抢走，只能由持有者主动释放。
  • 循环等待：几个线程之间形成了首尾相接的等待环路，比如 A 等 B，B 等 A。

程池的本质是一组固定的线程来反复执行多个任务，避免频繁创建和销毁线程带来的开销，是JUC中最核心的任务调度工具。

线程池

线程池及其代码示例

为什么用线程池

  • 降低资源消耗：复用线程，避免频繁创建和销毁线程的开销
  • 提高相应速度：任务达到时，直接由已有线程执行，避免等待创建
  • 便于线程统一管理

核心类与接口

  • Executor：顶层接口，只定义了 execute(Runnable) 方法。
  • ExecutorService：子接口，增加了 submit（可返回 Future）、shutdown 等生命周期管理方法。
  • ThreadPoolExecutor：核心实现类，几乎所有线程池都由它直接或间接创建。
  • Executors：工厂类，提供快速创建常见线程池的静态方法（不推荐生产直接使用，有 OOM 风险）。

核心参数

参数 含义
corePoolSize 核心线程数，即使空闲也不会被回收（除非设置 allowCoreThreadTimeOut）
maximumPoolSize 最大线程数，当队列满时能扩容到的上限
keepAliveTime 非核心线程的空闲存活时间，超时后被销毁
unit keepAliveTime 的时间单位
workQueue 工作队列，存放等待执行的任务
threadFactory 线程工厂，用于自定义线程名字、是否守护线程等
handler 拒绝策略，当线程池和队列都满时对新任务的拒绝方式

工作流程

当一个任务提交到线程池时，执行顺序如下：

  1. 先看核心线程：若当前线程数 < corePoolSize，直接创建新线程执行任务，即使有空闲线程也创建。
  2. 核心线程满了 → 进队列：若当前线程数 >= corePoolSize，任务被放入 workQueue 等待。
  3. 队列满了 → 扩容：若队列也满了，且当前线程数 < maximumPoolSize，创建非核心线程来执行任务。
  4. 全部满了 → 执行拒绝策略：若线程数已达到 maximumPoolSize 且队列已满，handler 来处理新任务。

通俗总结：核心线程 → 工作队列 → 最大线程 → 拒绝策略，逐级处理。

决绝策略

拒绝策略 行为
AbortPolicy（默认） 直接抛出 RejectedExecutionException 异常
CallerRunsPolicy 让调用者所在的线程来执行该任务，从而降低新任务的流量
DiscardPolicy 直接丢弃新任务，无任何通知
DiscardOldestPolicy 丢弃队列最前面的任务（最老的任务），然后重试提交当前任务

常用队列

  • SynchronousQueue：不存储任务，来一个必须立即处理，否则就扩容或拒绝。适合大量短任务高并发，搭配较大的 maximumPoolSize。
  • LinkedBlockingQueue：无界或有界链表队列。无界时队列几乎不会满，maximumPoolSize 参数失效，线程数最多就是 corePoolSize。
  • ArrayBlockingQueue：有界数组队列。可以配合合理的 corePoolSize 和 maximumPoolSize，防止资源耗尽，是生产环境常用的有界队列。
